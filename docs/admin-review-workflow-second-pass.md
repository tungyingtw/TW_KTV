# 後台管理流程第二輪巡檢紀錄

## 目標

檢查前台 Phase 5 收尾後，後台管理者在「待處理」、「使用者回報」、「已採納」、「已駁回」與舊投票審核標籤之間操作時是否仍有疑惑點。

## 本輪已檢查

- 檢查 `server/admin.html` 的後台標籤建立與命名。
- 檢查「待處理」資料卡片的來源、篩選、採納、駁回與查看來源流程。
- 檢查「已採納 / 已駁回」紀錄列表的來源跳轉設計。
- 檢查 `server/index.js` 的 `/api/admin/review-queue`、`/api/admin/review-actions` 與舊投票審核 API。

## 本輪已修正

- 將後台可見的「爭議投票」文案改為「收錄狀態待確認」，降低管理者理解成本。
- 將總覽說明中的「爭議票選」改為「收錄狀態待確認項目」。
- 修正「已採納 / 已駁回」紀錄中的「查看來源」：
  - report 來源直接切到「使用者回報」，並依 adopted/rejected 切換為 resolved/rejected 篩選。
  - availability vote 來源切到「收錄狀態待確認」。
  - guided vote 來源切到「導唱功能待確認」。
  - mv vote 來源切到「MV 類型待確認」。

## 合理流程定義

- 「待處理」必須是管理者日常處理入口。
- 「已採納」與「已駁回」必須是查詢紀錄，不作為主要操作入口。
- 舊投票審核標籤可保留，但標籤文案必須用資料意義命名，不要用「爭議投票」這類不明確詞彙。
- 已處理紀錄的「查看來源」必須能導向可理解的原始脈絡，即使該項目已不在待處理快取中。

## 尚未完成項目

- 尚未確認 Render 線上環境中 review action 與 report 狀態是否完全一致。
