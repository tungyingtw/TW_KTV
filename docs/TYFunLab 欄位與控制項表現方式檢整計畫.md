# TYFunLab 欄位與控制項表現方式檢整計畫

## 目標

把目前網站中的欄位、狀態、篩選與操作控制先分清楚，再決定哪些維持現況、哪些改成更適合的表現方式。執行時不得為了「看起來有改」而把原本清楚、可用、符合語意的元件硬改成不合適的控制項。

## 核心判斷

1. 將「資料狀態」和「操作控制」分開處理。
2. 將「收錄、MV、導唱」視為歌曲資料狀態；在列表、卡片、詳情頁中使用文字標籤、徽章、數字摘要或空狀態，不得改成開關。
3. 將「原版 MV、有導唱」篩選條件視為操作控制；在搜尋區與篩選面板中檢查是否由 checkbox 改成 toggle chip 或 segmented toggle 更適合。
4. 將「列表模式、小卡模式」視為檢視模式切換；維持 icon segmented control，不改成下拉選單或 checkbox。
5. 將「品牌選擇」視為多選/單選混合篩選；維持可橫向掃描的品牌 chip rail，不改成一般表單選單。
6. 將「我的歌本、提供建議、回報、預覽」視為動作；維持 button/link button，並用圖示與文字協助辨識。

## 表現方式指令

### 1. 篩選控制

將桌面搜尋區的「原版 MV」與「有導唱」從傳統 checkbox 評估改為 toggle chip。實作時讓 chip 保留原本 checkbox 的可及性語意，可以使用 `aria-pressed` 或保留隱藏 input，但視覺上呈現為可點選的狀態膠囊。

將手機 Bottom Sheet 中的「原版 MV」與「有導唱」評估為整列 toggle button，不使用 iOS/Android switch。這兩個條件是查詢篩選，不是永久設定；switch 會讓使用者誤以為是系統狀態。

保留語種與字數 chip。不得將語種改成 checkbox 清單，不得將字數改成下拉選單。

### 2. 狀態欄位

保留「收錄」作為狀態欄位名稱。不得改回「可唱」。不得把列表中的「收錄」狀態改成 switch、checkbox 或可操作控制。

將「有收錄」使用收錄專屬色。將「MV」使用影音/藍色系。將「導唱」使用導唱專屬色，與收錄色保持明顯差異。日光與夜間模式都要遵守同一套語意色。

手機列表先維持「歌曲 / 收錄 / MV / 導唱」四欄。若後續截圖顯示欄寬不足，再將「MV」與「導唱」合併成「版本」欄，並在同一格內用兩個小徽章呈現。不得在未驗證手機截圖前直接合併欄位。

桌面矩陣維持品牌欄位。不得將桌面矩陣改為只顯示摘要卡，因為使用者需要橫向比較多家 KTV 品牌。

### 3. 品牌與模式切換

品牌列維持 chip rail。保留左右箭頭與拖曳滑動。選取多個品牌時，明確顯示已選品牌數與目前比對邏輯。

將「任一有收錄 / 全部皆有」視為條件邏輯切換。保留短文字，不只使用圖示。檢查按鈕是否看起來像 secondary action，而不是一般文字連結。

列表模式與小卡模式維持 icon segmented control。active 狀態要比一般按鈕更明確，但不得用過重漸層造成 AI 感。

### 4. 表單與社群回報

提供建議表單中的 select 維持 select。選項牽涉資料分類，不用 chip 取代。

回報表單中的問題分類維持 radio 或清楚的選項列。不得把問題分類藏在 dropdown 裡，使用者回報時要一眼知道正在選哪一類。

歌曲詳情中的社群投票維持分列呈現：「收錄對照」、「導唱功能」、「MV 類型」。三者顏色、標題與結果摘要要分開，不得共用同一種醒目色。

### 5. 視覺限制

不得新增大型漸層背景、浮誇發光、過度玻璃擬態或只為裝飾的卡片。所有新表現必須讓 KTV 網站更活潑，但仍像查詢工具。

日光模式不得把彩色元素全部壓暗。調整時保留粉、青、藍、黃的語意活力，但控制飽和度與背景面積，避免整頁變成單一粉色或單一米色。

夜間模式不得讓所有狀態都偏粉。收錄、MV、導唱、回報、警示、品牌色必須分色。

## 分階段執行

### 第一階段：文件與判斷

完成本文件。不得修改 UI。讓使用者先確認欄位與控制項的方向是否符合期待。

### 第二階段：篩選控制試修

只處理桌面搜尋區與手機篩選面板的二元篩選控制。將「原版 MV」與「有導唱」改成更像篩選條件的 toggle chip / toggle row。維持狀態資料不變。

驗證桌面 1440px、手機 390px，日光與夜間模式都不可出現文字擠壓、錯位或色彩混淆。

### 第三階段：狀態徽章與表格掃描

只處理列表、小卡、詳情頁中的狀態徽章。統一收錄、MV、導唱三種狀態的色彩與層級。不得改動資料邏輯。

驗證手機列表與桌面矩陣是否仍能快速看出哪家有收錄、哪家有 MV、哪家有導唱。

### 第四階段：詳情頁與回報流程

只處理歌曲詳情、社群投票、回報、提供建議表單的欄位表現。保留明確表單控制，不追求全部 chip 化。

驗證使用者是否能順利完成：開啟詳情、收藏、投票、回報、提供建議。

## 驗收標準

1. `npm.cmd run build` 必須通過。
2. 手機 390px 日光/夜間截圖不得出現欄位文字擠壓或控制項誤判。
3. 桌面 1440px 日光/夜間截圖不得讓搜尋、品牌列、表格狀態看起來像不同設計系統。
4. 「收錄、MV、導唱」三種狀態在日夜模式中都必須能一眼分辨。
5. 篩選控制看起來必須像可操作控制；資料狀態看起來必須像資料狀態。
6. 不得移除現有核心功能，不得改資料結構，不得改 API 契約。

## 不處理項目

本階段不重做整體版面，不改品牌資料，不改搜尋邏輯，不改社群投票資料儲存方式，不清除既有文件。若後續要調整欄位名稱以外的文案，另開文案一致性階段處理。
